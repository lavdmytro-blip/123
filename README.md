# BingX AI Signals v1.4.0 — автоматическая ДЕМО-торговля (Railway)

**В этой версии добавлен новый режим Paper Trading. Это не подключение к реальному торговому аккаунту BingX.** Ни приватные API-ключи, ни ордера, ни биржевые средства не используются. Движок читает только общедоступные котировки и закрытые 1m-свечи, а все сделки и деньги **виртуальны**.

## Что нового

- Новая вкладка **«Демо-торговля»** в Telegram Mini App, стартовый баланс **1 000 виртуальных USDT** для каждого пользователя.
- По умолчанию **ВЫКЛЮЧЕНО**. Нажмите «Включить демо-торговлю» в Mini App через Telegram. Входы будут происходить только **по новым** автосигналам ПОСЛЕ включения; старые сигналы не проигрываются задним числом.
- Для каждого нового сигнала, прошедшего Balanced-фильтр (`quoteVolume` за сутки от 10 млн USDT, `launchTime` не моложе 30 дней, без нестандартных инструментов), открывается виртуальная позиция LONG/SHORT при наличии свободного баланса.
- Ограничение: **максимум 2** одновременные позиции, не больше **20% свободных средств** на новый вход и модельный **риск на стопе до 1%** от меньшей величины (стартовый баланс / свободный остаток), **без плеча (1×)**.
- Рассчёт условных исполнений: **0,05% комиссия за вход/выход** и **0,05% проскальзывание против позиции** на каждом заполнении. Финансирование, налоги, частичное реальное исполнение и задержки биржи не моделируются.
- Виртуальный выход по TP1/TP2/TP3 **частями по одной трети**, остаток — по SL. Если в одной минутной свече одновременно затронуты SL и следующий TP, результат помечается `AMBIGUOUS`, а расчёт по консервативному варианту **SL первым**. Если свечи пропущены, статус `DATA_GAP` — нельзя честно утверждать, какой уровень был задет; возможен ручной демо-выход по свежей котировке.
- Можно выключить новые входы, вручную закрыть виртуальную позицию, посмотреть историю, P&L с комиссиями и сбросить счёт **только** при выключенном демо-режиме и отсутствии открытых виртуальных позиций.
- Отправка уведомлений о виртуальных входах/закрытиях — в личный чат бота, если пользователь дал `/start` и включены общие уведомления.

## Как обновить существующий Railway

1. Распакуйте ZIP и загрузите **содержимое папки `bingx-ai-signals`** в корень существующего GitHub-репозитория, заменяя старые файлы. Не загружайте ZIP как один файл.
2. Нажмите **Commit changes**, дождитесь нового `Success` в Railway → Deployments.
3. Убедитесь, что сервис запущен **в одной реплике**, с `ENABLE_WORKER=true`, `AUTO_SIGNALS_ENABLED=true` и прежним `DATABASE_URL=${{Postgres.DATABASE_URL}}`.
4. **Новые Railway Variables не нужны.** Не меняйте `BOT_TOKEN`, `WEBHOOK_SECRET`, `PUBLIC_BASE_URL`. Не удаляйте PostgreSQL: новые таблицы (`paper_accounts`, `paper_positions`, `paper_fills`) создаются автоматически поверх существующей базы без удаления истории.
5. Закройте и снова откройте Mini App. Проверьте отметку **v1.4.0** и вкладку **«Демо-торговля»**, нажмите **«Включить демо-торговлю»**. Откройте приложение через Telegram, потому что персональный демо-счёт доступен только с проверенной Telegram-авторизацией.
6. Не увидите позицию сразу? Это нормально: автоматический сканер создаёт её только при появлении **нового подтверждённого** сигнала. Если активна настройка `AUTO_SIGNALS_UNIVERSE=CUSTOM`, используется только указанный список, иначе — все пары после Balanced-фильтра.
7. При проблемах: Railway → Deployments → **View Logs**. Для диагностики используйте `GET /api/health`, для авторизованного клиента Mini App — `GET /api/paper`.

**Методика и ограничения:** свечной backtest не равен реальному исполнению. Если приложение и BingX были недоступны дольше пяти часов, история для старых позиций может оказаться неполной; состояние `DATA_GAP` не придумывает удачный результат. Это статистическая демо-модель, не прогноз доходности и не реальная торговля. Полную React-сборку и доступность BingX после деплоя необходимо проверить на Railway. В этом окружении сборка React недоступна из-за отсутствия npm-зависимостей; Python-тесты выполняются офлайн.

## Обновление v1.3.3 — История виртуальных сделок (автосигналов)

В Mini App появилась отдельная вкладка **«История сделок»** (на телефоне — **«Сделки»**). Она показывает сохранённые автоматические LONG/SHORT-сценарии, а не исполненные реальные ордера. Прежняя вкладка переименована в «Мои анализы» и продолжает показывать ручные запросы пользователя.

- **API:** `GET /api/auto-history?page=1&page_size=20&outcome=COMPLETED`.
- `outcome=ALL|COMPLETED|TP3|STOP|AMBIGUOUS|STALE|EXPIRED|ACTIVE`.
- Можно фильтровать: `side=LONG|SHORT|ALL`, `symbol=BTC`, `date_from=YYYY-MM-DD`, `date_to=YYYY-MM-DD` (даты **создания** сигнала).
- Сервер возвращает `total`, `hasMore`, `items`, общую статистику по сохранённой базе и время завершения. `TP3 / известные исходы` считается только по TP3 и STOP, без неоднозначных/просроченных случаев, и **не означает доходность**.
- Старые записи **не скрываются** текущим фильтром ликвидности/возраста, даже если пара исключена из новых рекомендаций.
- При обновлении существующей БД добавляется nullable `auto_signals.finished_at` без удаления записей. Для старых завершённых сигналов без времени закрытия UI показывает ориентировочное время по последней проверенной минутной свече, а для иных записей — «Не сохранено».
- Процент движения от входа до TP3 или SL — **гипотетический**, без исполнения сделки, частичного закрытия, плеча, комиссий и проскальзывания.

### Обновление Railway с v1.3.2

Замените содержимое репозитория GitHub файлами этого архива, сохранив секреты в Railway Variables. Railway пересоберёт Dockerfile. **Не удаляйте PostgreSQL и не меняйте `DATABASE_URL`**, если хотите сохранить старую историю. Дополнительные Variables не нужны. После успешного деплоя откройте Mini App заново и проверьте отметку `v1.3.3` вверху.

Проверка API после развёртывания: `https://<ВАШ_ДОМЕН>/api/auto-history?outcome=COMPLETED`. JSON со списком и статистикой подтверждает доступность архива. Тесты: `cd backend && PYTHONPATH=. pytest -q`.

## Обновление v1.3.2 — BALANCED-фильтр для автосигналов и PUMP/DUMP

Этот пакет **обновляет рабочую версию v1.3.1**, добавляя выбранный фильтр рынка. Это **не полная версия v2.0 с новыми стратегиями и обучением** — такие функции пока не реализованы в этом архиве.

- `MARKET_FILTER_MODE=balanced`
- `MARKET_MIN_24H_USDT=10000000` (минимум $10 млн оборота **в котируемой валюте USDT за 24 часа** — поле `quoteVolume`)
- `MARKET_MIN_LISTING_DAYS=30` (по `launchTime` контракта в официальном BingX API)
- `MARKET_EXCLUDE_NONSTANDARD=true` (отсев производных, мультипликаторных и нестандартно именованных пар, включая `NCSKABNB2-USDT`)

Фильтр применяется к **автоматическому сканеру сценариев**, **детектору PUMP/DUMP**, **публичным лентам** и отправке новых автоматических уведомлений. Он НЕ открывает сделки, а ручной поиск любой стандартной биржевой пары для просмотра графика остаётся доступным.

**Правило безопасности данных:** если BingX не предоставляет достоверный `launchTime` или `quoteVolume`, автоматический монитор не допускает пару. Лимит 10 млн и возраст 30 дней не гарантируют безопасность монеты: фильтр снижает количество слабых/необычных рынков, но не устраняет риски рыночных движений.

После деплоя проверьте:

- `GET /api/market-filter` — актуальные настройки, `eligible`, `excluded`, `reasons`.
- `GET /api/auto-signals` — поле `marketFilter` и новые сценарии только по разрешённым парам.
- `GET /api/pump-events` — поле `marketFilter` и события только по разрешённым парам.

Для настройки Railway новые переменные необязательны (значения выше — **значения по умолчанию**). Если добавляете их вручную, не удаляйте существующие `BOT_TOKEN`, `DATABASE_URL`, `PUBLIC_BASE_URL`, `WEBHOOK_SECRET`.

Полная сборка React и запросы к реальному API BingX требуют проверки после деплоя. Серверные тесты используют имитации публичных ответов, а не открывают сделки.

# BingX AI Signals — Telegram Mini App / Railway

Полноценный исходный проект технического анализа публичных котировок **BingX USDT-M Perpetual**. Интерфейс React/TypeScript + Lightweight Charts, сервер Python/FastAPI, Telegram-бот через защищённый webhook, SQLAlchemy/PostgreSQL, опциональный Redis, необязательный модуль AI-комментариев.

**Режим строго read-only:** приложение не выполняет заявки, не запрашивает BingX API keys, не подключает кошельки и не обещает прибыль. LONG/SHORT/WAIT — технические сценарии на основании завершённых свечей, а не предложение торговать. Применение сценариев к реальным сделкам может привести к потере средств.

## Что работает

- Поиск **всех** USDT-пар из публичного `/contracts`, живые цены и 24-часовое изменение, рыночный список; мини-графики по часовым свечам.
- Свечной график с масштабированием и EMA 20/50/200, объёмами, 7 таймфреймами, линиями ENTRY/SL/TP1–TP3.
- Детерминированные расчёты RSI(14), MACD(12/26/9), EMA, Bollinger(20,2), ATR(14), объёма, локальных экстремумов, уровней; funding/OI/depth как дополнительные сведения (если получены).
- **LONG / SHORT / WAIT** по прозрачным правилам. Вход, стоп и цели определяются структурой цены, ATR и заданным соотношением риска/результата; если результат не обоснован, WAIT и пустые уровни.
- Публичный BingX REST без торгового API-ключа, прямой публичный WebSocket `BTC-USDT@ticker` с GZIP/Ping/Pong/reconnect и REST fallback.
- Вход через Telegram WebApp `initData` с серверной HMAC-проверкой. Без Telegram доступны только просмотр цен и анализ, но не пользовательские данные.
- История, избранное, настройки, ценовые уведомления, слежение за новыми сигналами, уведомления о TP/SL через Telegram. Настройки и данные сохраняются в Postgres.
- 1m-свечи для контроля прохождения целей. Если TP/SL внутри одной свечи, статус **AMBIGUOUS**, если недостаёт истории, **STALE**. Никакой выдуманной статистики.
- Redis-кеширование при заданном `REDIS_URL`, кеш в памяти иначе; ограничение запросов на endpoint, обработка ошибок, таймауты, кеш и проверка свежести данных.
- Необязательные AI-комментарии: при указании `OPENAI_API_KEY` сервер отправляет уже готовые аргументы в AI для **словесной** интерпретации. Без ключа отображаются полноценные алгоритмические объяснения, но не выдается текст за работу LLM.

## Как развернуть на Railway (один веб-сервис)

1. Распакуйте ZIP. Создайте **приватный репозиторий GitHub** и загрузите **содержимое папки `bingx-ai-signals`** в корень репозитория (Dockerfile должен лежать в корне).
2. Создайте новый проект на **Railway → New Project → Deploy from GitHub Repo**, подключите репозиторий. Railway распознает корневой `Dockerfile` и будет собирать и фронтенд, и сервер в одном контейнере. **Не устанавливайте Root Directory на `/frontend` или `/backend`.**
3. Добавьте в проект Railway **PostgreSQL** (New → Database → PostgreSQL). В переменных вашего приложения задайте `DATABASE_URL` ссылкой на `DATABASE_URL` PostgreSQL-сервиса, например `${{Postgres.DATABASE_URL}}` (имя `Postgres` может отличаться). Не используйте SQLite на Railway для постоянной истории: локальные файлы контейнера могут исчезнуть при редеплое.
4. В Railway → ваш сервис → **Settings → Networking → Generate Domain** получите HTTPS-адрес вида `https://xxxxx.up.railway.app`.
5. В Telegram откройте **@BotFather**, создайте собственного бота через `/newbot`. Скопируйте выданный токен — никому его не пересылайте и не добавляйте в Git.
6. В Railway → ваш сервис → Variables добавьте:

   | Переменная | Значение |
   |---|---|
   | `BOT_TOKEN` | Токен от BotFather |
   | `PUBLIC_BASE_URL` | Ваш **точный HTTPS-адрес** Railway, без завершающего `/` |
   | `WEBHOOK_SECRET` | Случайная строка из `A-Z a-z 0-9 _ -`, минимум 32 символа |
   | `DATABASE_URL` | Railway reference на Postgres, например `${{Postgres.DATABASE_URL}}` |
   | `ENABLE_WORKER` | `true` |
   | `REDIS_URL` | *Необязательно*: reference URL Redis из Railway |
   | `OPENAI_API_KEY` | *Необязательно*: только для дополнительных AI-комментариев |
   | `OPENAI_MODEL` | *Необязательно*: `gpt-4.1-mini` (можно изменить на поддерживаемую модель) |

7. После сохранения Railway автоматически редеплоит проект. Дождитесь статуса **Success**. Если нужно, нажмите Redeploy. Перейдите на `https://ваш-домен/api/health` — ожидается `{"status":"ok", "mode":"read-only", "bot":true}`.
8. Откройте **своего** Telegram-бота и отправьте `/start`. Появится кнопка **«Открыть Mini App»**, а также кнопка в меню чата. Telegram не требует ручного указания Mini App URL в BotFather для этой web_app-кнопки: сервер устанавливает menu button через Bot API.
9. Если бот не отвечает, посмотрите **Railway → Deployments → View Logs**. Проверьте `BOT_TOKEN`, `PUBLIC_BASE_URL` и `WEBHOOK_SECRET`. Если сайт открывается, но нет цен — проверьте доступность публичного BingX API из выбранного региона Railway и сообщения об ошибке.

### Что важно в Railway

- Запускайте **ровно одну реплику** сервиса: встроенный фоновой обработчик отслеживает сигналы и отправляет уведомления. Для масштабирования перенесите `worker.loop` в отдельный сервис с распределённой блокировкой.
- Укажите `DATABASE_URL`, иначе используется SQLite только для локальной разработки; на Railway это непостоянный том контейнера.
- Redis необязателен: без него работает кеш внутри приложения; с ним кеш переживает вызовы между обработчиками.
- Для HTTPS ничего отдельно настраивать не требуется: публичный домен предоставляет Railway.
- Секреты — **только** Railway Variables; не записывайте их в frontend или .env в GitHub.
- Уведомления от бота возможны только если пользователь **начал диалог `/start`** и разрешил уведомления.

## Локальный запуск

В двух терминалах:

**Backend** (Python 3.12+):

```bash
cd backend
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows PowerShell: .venv\\Scripts\\Activate.ps1
pip install -r requirements.txt
# BOT_TOKEN можно не задавать для гостевого анализа
uvicorn app.main:app --host 127.0.0.1 --port 8080 --reload
```

**Frontend** (Node.js 20+):

```bash
cd frontend
npm install
npm run dev
```

Откройте `http://localhost:5173`. Vite пересылает `/api` на FastAPI. В обычном браузере доступен гостевой режим; персональные функции требуют запуска внутри Telegram.

Проверить Python-часть:

```bash
cd backend
pytest -q
```

## Что делает аналитический алгоритм

- Для EMA 200 необходимо минимум **210 закрытых свечей**, для 1d это несколько месяцев исторических данных.
- Незавершённая последняя свеча **не участвует** в расчётах; устаревшая история отвергается.
- Веса: EMA trend 3, MACD momentum 2, RSI 1, объём 1, локальная структура 1. LONG/SHORT — минимум 6 баллов и минимум на 4 больше противоположной стороны; иначе WAIT.
- Стоп рассчитывается от локальной структуры и ATR, минимально 1.5 ATR; TP1/TP2/TP3 ориентируются на 1.5R, 2R, 3R. Если сопротивление/поддержка слишком близко, риск слишком велик или цены некорректны, результат WAIT.
- Funding, open interest, стакан служат контекстом. Они **не подменяют** исторические данные и не создают ложное ощущение точности.
- Сила сигнала 0–8 — **не** вероятность прибыли. Это лишь сумма голосов алгоритма.
- История подсчитывает подтверждённые TP1/TP2/TP3 и SL. Невозможность восстановить внутрисвечной порядок имеет отдельный статус.

**Ограничения текущей версии:** текст интерфейса преимущественно русский; настройка `EN` сохраняется, полноценная англоязычная локализация пока не реализована. Уведомления и проверка исходов выполняются фоновым циклом примерно каждые 90 секунд, обнаружение новых направлений — примерно каждые 6 минут, с лимитом `MAX_SCAN_WATCHES`. Проверка срабатываний использует минутные OHLC, не биржевой журнал сделок; если сервис долго не работает или история недоступна, исход может остаться непроверенным. Никакой полноценной AI-модели без отдельного ключа нет. Перед публичным запуском на большое число пользователей желательно добавить распределённую очередь задач, наблюдаемость и нагрузочное тестирование.

## Обновление v1.2 — весь рынок, прогресс сканирования и иконки

- По умолчанию `AUTO_SIGNALS_UNIVERSE=ALL`: фоновый сканер последовательно обходит **все доступные BingX USDT-M бессрочные пары** из `/contracts`, а не только старый список из 5. Старое значение `AUTO_SIGNALS_SYMBOLS` **игнорируется**, пока явно не указано `AUTO_SIGNALS_UNIVERSE=CUSTOM`. Поэтому при обновлении Railway не требуется удалять старую переменную.
- Сканирование вынесено в **отдельную asyncio-задачу**: обход нескольких сотен монет не блокирует основной цикл отслеживания TP/SL. Приоритет у популярных пар, остальные обрабатываются по торговому объёму 24ч. Отдельный фоновый обход занимает время и ограничен лимитами BingX: это **не одновременное обновление тысяч монет**. Прогресс отображается как `проверено X из Y`, частями по `AUTO_SCAN_BATCH_SIZE` (по умолчанию 12); пауза между запросами `AUTO_SCAN_PACE_SECONDS=1.2`; в конце обхода — `AUTO_SCAN_COOLDOWN_SECONDS=60`. Лимит запросов встроен и в BingX клиент (порядка 1 запроса/сек на endpoint). Повышение скорости может вызвать rate-limit ошибки.
- Не публикуются сценарии на устаревших данных, при отсутствии сильного технического сигнала, при слишком сильном расхождении цены и зоны входа или когда активный сценарий по монете уже есть. Лента **может быть пустой** — это не ошибка.
- Вкладка «AI Сигналы»: фильтры **все / ТОП-20 по объёму / избранные**, **LONG / SHORT**, активные / все, поиск, сортировка по дате, силе, объёму и изменению цены. Для SHORT процент изменения теперь показывает направление виртуального сценария с правильным знаком.
- Появились настоящие логотипы монет (данные CoinGecko, 12-часовой серверный кеш). Если внешний API недоступен — используются публичные изображения из проекта `spothq/cryptocurrency-icons`. Для неподдерживаемых монет показывается **нейтральный значок монеты**, не буква и не придуманный чужой логотип. Покрытие реальных логотипов не гарантируется для каждой малоизвестной пары и тикеры иногда неоднозначны.
- Логотипы отображаются в поиске, обзоре, терминале, истории, уведомлениях и ленте. Текущее состояние сканера через `GET /api/auto-signals` включает `scanner` с общим числом пар и прогрессом; `GET /api/coin-logos` отдаёт кешированный каталог изображений.
- TP/SL по-прежнему **виртуальные**, подтверждаются по 1m OHLC с задержкой и возможными статусами STALE / AMBIGUOUS. Живые котировки отображаются по WebSocket только для части видимых монет, остальные обновляются REST примерно раз в 12 секунд. **Это не торговый робот, никаких ордеров или ключей BingX нет.**

Для Railway RAW Editor достаточно добавить/обновить:

```env
AUTO_SIGNALS_ENABLED=true
AUTO_SIGNALS_UNIVERSE=ALL
AUTO_SIGNALS_INTERVAL=15m
AUTO_SCAN_BATCH_SIZE=12
AUTO_SCAN_PACE_SECONDS=1.2
AUTO_SCAN_COOLDOWN_SECONDS=60
ENABLE_WORKER=true
```

Другие переменные (`BOT_TOKEN`, `DATABASE_URL`, `PUBLIC_BASE_URL`, `WEBHOOK_SECRET`) сохраняются как раньше. Дополнительная таблица прогресса `scanner_state` создаётся автоматически; старые сигналы не удаляются. Оставьте **одну реплику** Railway: при нескольких копиях приложения встроенные worker и scanner конкурируют и могут публиковать дубликаты.

Источники логотипов: https://www.coingecko.com/en/api , https://github.com/spothq/cryptocurrency-icons (применимые условия использования и лицензии относятся к соответствующим источникам).

## Обновление v1.1 — живые свечи и автоматическая лента сигналов

- В терминале для выбранной пары и периода подписка WebSocket теперь идёт на **`{symbol}@kline_{interval}`**. Обновление свечи не пересоздаёт график и не сбрасывает масштаб. При переключении таймфрейма запрашиваются соответствующие свечи и открывается новая WebSocket-подписка. Состояния LIVE / CONNECTING / REST FALLBACK показывают способ обновления; если соединение оборвалось, резерв — REST (примерно раз в 20 секунд).
- Отдельная вкладка **«AI Сигналы»** публикует **автоматически найденные виртуальные** LONG/SHORT-сценарии только при достаточно сильном согласии технических индикаторов. По умолчанию сканирует BTC, ETH, SOL, XRP и BNB на 15m **примерно каждые 3 минуты** при `ENABLE_WORKER=true`. Сканер не создаёт сигнал, если нет подтверждений, если цена сильно ушла от последней завершённой свечи, или если по паре ещё есть активный сценарий. Возможны длительные периоды без новых сигналов — это нормально.
- Сохраняет цену в момент сценария, три цели, уровень отмены (SL), время, статус и вывод анализа в PostgreSQL. В разделе отображаются котировка BingX с WebSocket (при отключении — REST polling), процент движения от entry и прогресс к TP1. **Само подтверждение TP/SL производится фоновым worker по завершённым 1m свечам**, поэтому может запаздывать. Нет реального открытия или закрытия ордеров.
- Встроена защита от дубликатов по свече (уникальное ограничение в БД), от публикации устаревших сигналов, от разрыва истории для последующей проверки (STALE). Если TP и SL были в одной минутной свече — AMBIGUOUS. Активные сценарии автоматически получают статус EXPIRED после 24 часов. Пользователь может открыть соответствующий график и увидеть уровни.
- Новые сообщения о публичных автосигналах отправляются в Telegram **только после нажатия пользователем «Уведомлять в Telegram»**, если чат уже связан через `/start`. Вкладка и публичная лента работают также без авторизации.
- Если задан `OPENAI_API_KEY`, добавляется короткое AI-объяснение причин **без придумывания котировок или новых чисел**. Без ключа сигналы определяет правилами прозрачный технический алгоритм; отдельная LLM не используется.

## v1.3 — PUMP / DUMP и уведомления в Telegram

Добавлена вторая вкладка внутри **«AI Сигналы» → «PUMP / DUMP»**. Это **наблюдение уже произошедших рыночных движений**, а не прогноз или команда на открытие сделки:

- Монитор опрашивает публичный all-market `BingX /openApi/swap/v2/quote/ticker` приблизительно раз в 20 секунд; один запрос охватывает все доступные USDT-пары.
- Сравнивает цену с реально записанным наблюдением около 5 минут назад, с допустимым отклонением в 60 секунд. После перезапуска сервера нужно накопить 5 минут истории; 24-часовое изменение **не выдаётся** за пятиминутное.
- Предварительное событие: движение цены >=3% за ~5 минут и 24-часовой объём USDT >=100 000.
- Подтверждение: последняя пятёрка **закрытых минутных свечей**, торговый оборот за 5 минут >=20 000 USDT и объём за пять минут >=2× среднего по предыдущим четырём 5-минутным блокам. Для проверки свечи запрашиваются **только по кандидатам**.
- Публикует в ленту реальную наблюдаемую цену, изменение, кратность объёма, оборот, время и название пары. Пометка `PUMP` или `DUMP` **не означает доказанную рыночную манипуляцию**.
- На один инструмент и направление действует антиспам-пауза 30 минут, включая учёт событий в PostgreSQL после перезапуска.
- Отдельная кнопка **«Уведомлять в Telegram»** подписывает на PUMP/DUMP; сообщения приходят только в **личный чат бота** после `/start`. Нажми `/start` в чате, открой Mini App, перейди в «AI Сигналы → PUMP / DUMP» и включи уведомления. Если нужно отключить — нажми эту кнопку ещё раз.
- У обычных AI-сценариев Telegram-сообщения дополнены ENTRY, TP1–TP3 и SL, а при подтверждении цели/стопа отправляется статус. Обе подписки независимы; глобальное отключение уведомлений в настройках отключает доставку.
- В сообщениях есть кнопка **«Открыть график в Mini App»**. Она открывает терминал на нужной монете; это работает в личной переписке с ботом.
- Нет доступа к торговому счёту, автоматического исполнения сделок или обмена активами. Для публикации **не требуется** `OPENAI_API_KEY` — аналитика детерминирована.

## v1.4.2: Почему нет демо-позиций

Вкладка **Демо** показывает диагностику автосканера: статус фонового worker, количество допущенных BingX-пар, прогресс проверки, количество сигналов в текущей ленте и ошибки сервера.
